Remarks

When registered via AddEfCoreAuditing, this is a process-wide singleton shared by every scoped DbContext/interceptor instance. ValueSerializer and EntityKeySerializer are lazily defaulted (??=) by the first AuditingDbContext or AuditSaveChangesInterceptor constructed against this instance; that default-assignment is an unsynchronized check-then-write against the shared singleton. In practice every writer converges on a functionally-equivalent default instance, so this is benign, but it is not formally thread-safe — avoid mutating an already-registered AuditOptions after startup from application code.

Properties

BulkInsertRowThreshold

Minimum number of pending audit headers in a single save before the interceptor tries a provider-specific bulk-insert fast path instead of the normal EF Core tracked-entity insert. null (the default) disables bulk insert entirely — every save uses the standard path regardless of size.

public int? BulkInsertRowThreshold { get; set; }

Property Value

int?

Remarks

Only takes effect when a provider-specific IAuditBulkWriter is registered (e.g. via a provider integration package) AND that writer's CanHandle returns true for the current context. Providers with no registered writer, or a writer that declines, always use the standard EF Core insert path regardless of this threshold.

CaptureDeletedValues

When true, Delete operations write detail rows containing the pre-delete column values. When false (the default), Delete operations write only a header row.

public bool CaptureDeletedValues { get; set; }

Property Value

bool

Remarks

Important — stub-attached deletes: the captured values come from PropertyEntry.OriginalValue, which is meaningful only when the entity was actually loaded (or had its originals seeded) before deletion. The classic "stub delete" pattern — 

context.Set<Customer>().Remove(new Customer { Id = 5 })

— attaches an entity whose non-key properties are CLR defaults, so the detail rows would record those defaults rather than the actual row state. When this flag is on, consumers should load the row first (or call entry.Reload()) before removing it. The captured values are fundamentally a snapshot of what EF Core knew at delete time, not a database read-back.
